# ResearchMatch — Offline-First Grad School Assistant (Elasticsearch + Ollama)

**One-liner:** ResearchMatch is a grad-school discovery assistant that answers questions about **faculty fit**, **programs**, and **application deadlines** using a **one-time offline snapshot dataset** stored in **Elasticsearch**, with responses generated by a **local LLM via Ollama**.

> For installation and local environment steps, see **[LOCAL_SETUP.md](LOCAL_SETUP.md)**.

---

## 1) Core Philosophy: Static Snapshot (Offline-First)

We are **not** building a real-time web search engine.

Live scraping during a demo is risky (rate limits, Cloudflare, slow pages, unpredictable results). Instead, we:
- Build a **static snapshot dataset** offline (CSV files).
- Ingest the snapshot into **Elasticsearch**.
- Run a Streamlit chatbot UI that searches Elasticsearch and uses **Ollama** to produce grounded answers.

### Data Policy (Important)
- **Append-only** while developing (we can add new schools/programs/faculty).
- We do **not update/refresh existing records** from the internet once they are created.
- Before final demo, we freeze a **Golden Dataset** and re-ingest from it for consistency.

---

## 2) What We Are Building (Scope)

### MVP Capabilities
The assistant should handle:
- “What are the **PhD deadlines** for University X?”
- “Show **top programs** in Y research area and their deadlines.”
- “Which **faculty** at School Z do **NLP/security/systems**?”
- “Filter programs by **deadline range** and degree level (MS vs PhD).”
- “Show faculty marked as **recruiting** (demo field).”

### Non-Goals (for this capstone timeline)
- No live scraping at query-time
- No automatic weekly updates
- No claims of authoritative “recruiting status” unless sourced (we may simulate it)

## 3) Architecture (How It Works)

```
User (Streamlit UI)
   |
   v
Query Router (Python)
   |
   v
Elasticsearch (retrieval over snapshot data)
   |
   v
Context Packager (top-k JSON docs)
   |
   v
Ollama (local LLM) -> grounded response
   |
   v
Streamlit UI (formatted answer + sources)
```

**Key rule:** Elasticsearch retrieves the facts; the LLM uses **only retrieved context** to answer.

## 6) Elasticsearch Indices & Schemas

We use **three indices** (keeps queries simple and avoids nested complexity):

### 6.1 `universities` (one doc per university)
**Required fields**
- `university_id` (string, stable key; e.g., `uw`, `stanford`)
- `name` (string)
- `country` (string)
- `website` (string, optional)
- `snapshot_version` (string, e.g., `v1`)
- `created_at` (date)

Example:
```json
{
  "university_id": "uw",
  "name": "University of Washington",
  "country": "USA",
  "website": "https://www.washington.edu/",
  "snapshot_version": "v1",
  "created_at": "2026-02-10"
}
```

### 6.2 `programs` (one doc per program; MS/PhD separate)
**Required fields**
- `program_id` (string; e.g., `uw_cs_phd`)
- `university_id` (string)
- `program_name` (string)
- `degree_level` (enum: `MS`, `PhD`)
- `term` (string; e.g., `Fall 2026`)
- `deadlines.priority` (date, optional)
- `deadlines.final` (date, optional)
- `requirements.gre_required` (enum: `required`, `optional`, `not_required`, optional)
- `source_url` (string, optional)
- `snapshot_version` (string)
- `created_at` (date)

Example:
```json
{
  "program_id": "uw_cs_phd",
  "university_id": "uw",
  "program_name": "Computer Science PhD",
  "degree_level": "PhD",
  "term": "Fall 2026",
  "deadlines": {
    "priority": "2025-12-01",
    "final": "2026-01-05",
    "notes": "Priority deadline for funding consideration."
  },
  "requirements": {
    "letters_required": 3,
    "statement_required": true,
    "gre_required": "optional",
    "english_test": {
      "toefl_min": 92,
      "ielts_min": 7.0
    }
  },
  "source_url": "https://example.edu/cs/phd/admissions",
  "snapshot_version": "v1",
  "created_at": "2026-02-10"
}
```

### 6.3 `faculty` (one doc per faculty member)
**Required fields**
- `faculty_id` (string; stable key)
- `name` (string)
- `university_id` (string)
- `research_areas` (array of strings; normalized tags)
- `csrankings_areas` (array of strings, optional)
- `homepage_url` (string, optional)
- `hiring_status` (enum: `Active`, `Inactive`) **(demo/simulated unless sourced)**
- `snapshot_version` (string)
- `created_at` (date)

Example:
```json
{
  "faculty_id": "uw_jane_doe",
  "name": "Jane Doe",
  "university_id": "uw",
  "research_areas": ["machine learning", "nlp"],
  "csrankings_areas": ["ai", "nlp"],
  "homepage_url": "https://example.edu/~janedoe",
  "hiring_status": "Active",
  "snapshot_version": "v1",
  "created_at": "2026-02-10"
}
```

## 7) Search + LLM Behavior (Grounded Answers)

We do **structured retrieval + grounded generation**:

1) Convert user question → **Elasticsearch query**
2) Retrieve top-k program/faculty/university records
3) Pass those records as **context** into Ollama
4) LLM produces a **formatted answer** and **must not invent info**

If there are no matching records, the assistant must say:
> “Not in our snapshot dataset.”

Implementation details (how to run the stack, pinned Docker versions, environment variables, etc.) are documented in **[LOCAL_SETUP.md](LOCAL_SETUP.md)**.

## 8) Execution Timeline (Roles + Dependencies + Workflow + Deliverables)

This section combines the project timeline with **who does what**, **what each role must be able to run**, and **what must be produced** by the end of each timebox.

> **Core rule:** Everyone should ultimately be able to run the full stack end-to-end (Docker → ingest → Ollama → Streamlit), but each sprint has clear owners per role.

---

### Timebox 2 — Foundation (Hello World)
**Goal:** Prove the pipeline works end-to-end: **CSV → Elasticsearch → query returns correct JSON**.

#### Role workflow (what gets done)
- **P1 — Data Engineer**
  - Create pilot snapshot for **5 schools** in `data/working/` (or directly in `data/golden/` if you’re ready).
  - Ensure:
    - stable IDs (`university_id`, `program_id`, `faculty_id`)
    - dates in `YYYY-MM-DD`
    - basic `source_url` fields where available
- **P2 — Backend / DevOps**
  - Ensure the Docker stack runs reliably.
  - Implement:
    - `scripts/create_indices.py`
    - `scripts/ingest.py`
    - `scripts/reset_db.py` (delete → recreate → ingest)
- **P3 — App Developer (Streamlit + Ollama Integration)**
  - Create a minimal retrieval test that queries Elasticsearch for a known entity (e.g., “Stanford”).
  - Set up Streamlit skeleton UI (input + output placeholder).
  - Confirm local Ollama can be called from Python.
- **P4 — QA & Presenter**
  - Run the stack on a **second laptop** (fresh environment).
  - Verify data appears in Kibana.
  - Capture screenshots for slides and write “known issues” notes.

#### Dependencies (what each person must have working)
- **P1:** Python + pandas
- **P2:** Docker + Compose
- **P3:** Streamlit + Ollama; model pulled successfully
- **P4:** Can run the full stack on a clean machine

#### Deliverables (definition of done)
- Docker stack runs on **2 machines**
- `reset_db.py` successfully ingests pilot data
- a test query returns correct JSON from Elasticsearch
- minimal Streamlit app starts without crashing

---

### Timebox 3 — Prototype (Chat UI + Grounded LLM)
**Goal:** A working chatbot UI that answers from **Elasticsearch context via Ollama**.

#### Role workflow (what gets done)
- **P1 — Data Engineer**
  - Expand to **~20 schools** in `data/working/` (append-only).
  - Standardize:
    - degree level (`MS`, `PhD`)
    - term naming (e.g., `Fall 2026`)
    - deadline fields (`priority`, `final`)
- **P2 — Backend / DevOps**
  - Finalize index mappings so queries/filtering are consistent.
  - Improve ingestion reliability (bulk ingest, clear error logs).
- **P3 — App Developer (Streamlit + Ollama Integration)**
  - Implement a working chat flow:
    1) classify intent (program vs faculty vs university)
    2) run ES retrieval
    3) package top-k docs into context
    4) call Ollama with the grounding prompt
    5) render formatted response
  - Ensure formatting rules:
    - deadlines are **bold**
    - include `source_url` when present
- **P4 — QA & Presenter**
  - “Red team” the bot:
    - ask about schools not in the dataset → must say **Not in our snapshot dataset**
    - ask confusing/multi-part queries → bot must not invent facts
  - Draft the demo narrative (3–5 questions that show value).

#### Deliverables (definition of done)
- Streamlit chatbot UI connected end-to-end
- Ollama always used for responses (grounded prompt)
- “I don’t know” behavior works reliably
- Dataset expanded to ~20 schools
